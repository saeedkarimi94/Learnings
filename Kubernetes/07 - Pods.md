# پاد، Pods (کوچک‌ترین واحد قابل‌استقرار در کوبرنتیز)

در کوبرنتیز شما هرگز یک «کانتینر» را مستقیماً دیپلوی نمی‌کنید! کوچک‌ترین آجری که کوبرنتیز می‌شناسد، خلق می‌کند، مانیتور می‌کند و از بین می‌برد، **پاد (Pod)** است.

---

## 1. پاد (Pod) دقیقاً چیست و چرا مستقیماً کانتینر نداریم؟

### 1.1 یک تشبیه ملموس (غلاف نخودفرنگی / Pod of Peas)
واژه **Pod** در زبان انگلیسی به معنای «غلاف یا غلاف نخودفرنگی» است؛ همان پوسته بیرونی که چند دانه نخود را کنار هم محکم در یک محیط محافظت‌شده نگه می‌دارد:
* **غلاف بیرونی:** همان Pod است.
* **دانه‌های داخل غلاف:** کانتینرها (Containers) هستند.

یک پاد می‌تواند **تک‌کانتینری (Single-container)** باشد (که 90٪ مواقع همین است؛ مثلاً فقط یک کانتینر Nginx)، یا **چندکانتینری (Multi-container)** باشد (یک کانتینر اصلی مثل وب‌اپلیکیشن + یک کانتینر کمکی مثل لاگ‌جمع‌کن یا Sidecar).

---

### 1.2 چرا کوبرنتیز مستقیماً Container را اجرا نمی‌کند؟ (فلسفه وجودی پاد)
کوبرنتیز به کانتینرها به چشم پردازه‌های ساده نگاه نمی‌کند؛ بلکه برای مدیریت ارتباطات، نیاز به یک لایه انتزاعی بالاتر داشت. وقتی دو کانتینر داخل یک پاد قرار می‌گیرند:

1. **یک آدرس IP مشترک دارند:** کل پاد یک IP منحصربه‌فرد در کلاستر دریافت می‌کند.
2. **یک Network Namespace مشترک دارند:** کانتینرهای داخل یک پاد می‌توانند از طریق `localhost` و پورت‌های مختلف به سادگی با هم صحبت کنند (درست مثل دو پردازه روی یک سرور لینوکسی واحد).
3. **می‌توانند دیسک (Storage Volume) مشترک داشته باشند:** یک دیسک در پاد تعریف می‌شود و هر دو کانتینر می‌توانند هم‌زمان روی آن فایل بخوانند و بنویسند.
4. **سرنوشت و چرخه حیات مشترک دارند (Fate Sharing):** با هم روی یک نود زمان‌بندی می‌شوند، با هم بالا می‌آیند و اگر نود بمیرد، کل پاد با تمام کانتینرهایش با هم جابجا می‌شوند.

---

## 2. چهار ستون اصلی هر فایل YAML در کوبرنتیز (The Top-Level Fields)

در تمام آبجکت‌های کوبرنتیز (پاد، سرویس، دیپلویمنت و...)، ساختار مانیفست YAML از **4 کلید ریشه‌ای و بنیادین** تشکیل شده است:
```bash
apiVersion: v1        # نسخه API که این آبجکت را تعریف می‌کند
kind: Pod             # نوع آبجکتی که می‌خواهیم بسازیم
metadata:             # مشخصات هویتی (شناسنامه پاد)
  name: my-first-pod
  labels:
app: web
spec:                 # مشخصات فنی و وضعیت مطلوب (ما چه می‌خواهیم؟)
  containers:
- name: nginx-container
image: nginx:1.25
ports:
- containerPort: 80
```

---

### 2.1 کالبدشکافی ۴ بخش:
1. apiVersion: مشخص می‌کند از کدام نگارش API سرور برای خواندن این آبجکت استفاده شود. برای Core Objects (مثل Pod، Service، Namespace) همیشه مقدار v1 است.
2. kind: نوع آبجکت است (با حروف اول بزرگ، مثل Pod، Service، Deployment).
3. metadata: اطلاعات شناسایی آبجکت شامل name، namespace و برچسب‌ها (labels).
4. spec (کوتاه‌شده‌ی Specification): نقشه فنی و قلب مانیفست. دقیقاً مشخص می‌کنیم چه ایمیجی، چند پردازنده، چه پورتی و چه ولومی باید برای کانتینرها تنظیم شود.
