# Control Plane Architecture
در این بخش اجزای اصلی مغز متفکر کلاستر (Control Plane) را بررسی می‌کنیم.
---
### مشاهده پادهای سیستمی
- برای مشاهده پادهای سیستمی از دستور زیر استفاده می‌کنیم
```bash
kubectl get pod -n kube-system
```
در خروجی دستور بالا پادهای سیستمی رو میبینید که مهمترین آن‌ها موارد زیر ‌می‌باشند و در صورتی که هرکدام از موارد زیر بالا نباشه کل کلاستر به مشکل بر میخورد:
```bash
karimi@Public-Agent12:~$ kubectl get pod -n kube-system
NAME                                     READY   STATUS    RESTARTS     AGE
etcd-public-agent12                      1/1     Running   0            13d
kube-apiserver-public-agent12            1/1     Running   0            13d
kube-controller-manager-public-agent12   1/1     Running   3 (6d ago)   13d
kube-scheduler-public-agent12            1/1     Running   3 (6d ago)   13d
```
#### نکته: برای exec کردن پاد مورد نظر از دستور زیر استفاده می‌کنیم:
```bash
kubectl exec -it -n <nsname> <podname> -- bash/sh
kubectl exec -it -n kube-system etcd-public-agent12 sh
```
---
## 1. etcd
- **تعریف:** یک پایگاه داده Key-Value توزیع شده و فوق‌سریع.
- **وظیفه:** ذخیره وضعیت (State) کل کلاستر. اگر etcd نباشد، کوبرنتیز هیچ چیزی از کلاستر نمی‌داند.
- **نکته کلیدی:** تنها جزء کلاستر است که وضعیت را در دیسک ذخیره می‌کند (Stateful). بقیه اجزا Stateless هستند.
---
## 2. API Server
- **وظیفه:** تنها قطعه‌ای است که با etcd صحبت می‌کند. تمام دستورات kubectl به اینجا می‌آید.
- **نقش:** احراز هویت (Auth) و اعتبارسنجی (Validation) درخواست‌ها.
---
## 3. Controller Manager
- **وظیفه:** بررسی حلقه کنترلی (Control Loop). 
- **مثال:** اگر در etcd نوشته شده 3 تا پاد باید باشد، اما الان 2 تا داریم، Controller Manager می‌فهمد که باید یکی دیگر بسازد و به Scheduler دستور می‌دهد.
---
## 4. Scheduler
- **وظیفه:** تصمیم می‌گیرد هر پاد روی کدام Worker Node قرار بگیرد (با توجه به منابع مثل CPU و RAM).
---
### نکته:فایل‌های سیستمی به صورت پیشفرش در دایرکتوری زیر ذخیره می‌شوند:
`/etc/kubernetes/manifests/`<br>
├── etcd.yaml<br>
├── kube-apiserver.yaml<br>
├── kube-controller-manager.yaml<br>
└── kube-scheduler.yaml<br>

## 1. بررسی عمیق etcd (مغز حافظه و منبع حقیقت کلاستر)
اگر API Server را زبانِ کوبرنتیز و Controller Manager را دست‌های اجرایی آن بدانیم، بدون شک **etcd حافظه دائمی (Single Source of Truth) کلاستر** است. تمام چیزهایی که در کلاستر وجود دارند—از تعریف پادها، نودها، سکرت‌ها، کانفیگ‌مپ‌ها تا وضعیت لحظه‌ای منابع—همگی در etcd ذخیره می‌شوند.

---
### 1.1 مفاهیم کلیدی و ویژگی‌های بنیادین etcd

1. **مدل داده‌ای کلید-مقدار (Key-Value Store):**
   - برخلاف دیتابیس‌های رابطه‌ای (مثل PostgreSQL یا MSSQL) که جدول و ردیف دارند، etcd داده‌ها را مثل یک دیکشنری ساخت‌یافته و درختی به صورت `Key: Value` نگه می‌دارد (مشابه ساختار دایرکتوری در لینوکس؛ مثل `/registry/pods/default/mypod`).

2. **تنها کامپوننت باوضعیت (Stateful):**
   - تمام قطعات دیگر Control Plane کاملاً Stateless هستند؛ یعنی اگر API Server، Scheduler یا Controller Manager ریستارت شوند، هیچ اطلاعاتی از دست نمی‌رود چون همه‌چیز دوباره از etcd خوانده می‌شود. اما اگر دیتای etcd بپرد، **کل کلاستر می‌میرد!**

3. **الگوریتم اجماع رفت (Raft Consensus Algorithm):**
   - در حالت چندمستری (HA)، دیتابیس etcd به‌صورت کلاستر (معمولاً 3 یا 5 نود) راه‌اندازی می‌شود.
   - بر اساس الگوریتم Raft، همیشه یک عضو **Leader** است و بقیه **Follower**. هر تغییری زمانی تایید می‌شود که اکثریت اعضا (Quorum) آن را تایید و ثبت کنند:
     $$\text{Quorum} = \left\lfloor \frac{N}{2} \right\rfloor + 1$$
     *(مثلاً در کلاستر 3 نودی، حداقل 2 نود باید همیشه زنده باشند).*

4. **تضمین پایداری و ثبات بالا (Strong Consistency):**
   - کوبرنتیز برای تصمیم‌گیری حیاتی به شدت به داده‌های دقیق و لحظه‌ای وابسته است. etcd تضمین می‌کند هیچ دو کلاینتی داده متناقض دریافت نکنند.

---
### 1.2 بررسی فایل مانیفست etcd.yaml
مانیفست این کامپوننت به شکل **Static Pod** در مسیر `/etc/kubernetes/manifests/etcd.yaml` روی نود مستر قرار دارد:
```bash
cat /etc/kubernetes/manifests/etcd.yaml
```
* `--secure-port=6443`
  - پورت اصلی و امن ارتباط با API Server. تمام ترافیک ورودی به کلاستر (از سمت kubectl یا ورکرها) روی این پورت شنود می‌شود.
* `--data-dir=/var/lib/etcd`
  - مسیری روی دیسک سرور فیزیکی که دیتای دیتابیس در آن ذخیره می‌شود. (این مسیر مهم‌ترین پوشه برای تهیه بکاپ دوره‌ای از کلاستر است).
* `--listen-client-urls=https://127.0.0.1:2379,https://<MASTER_IP>:2379`
  - پورت 2379 پورت ارتباط کلاینت‌ها (در رأس آن‌ها kube-apiserver) با دیتابیس است. این فلگ مشخص می‌کند دیتابیس روی چه آدرس‌هایی به درخواست‌های کلاینت گوش دهد.
* `--advertise-client-urls=https://<MASTER_IP>:2379`
  - آدرسی که دیتابیس به بقیه اجزا (مثلاً سایر مستر نودها برای اتصال API Serverهایشان) اعلام می‌کند تا بتوانند به آن وصل شوند.
* `--listen-peer-urls=https://<MASTER_IP>:2380`
  - پورت 2380 پورت اختصاصی برای صحبتِ درونی اعضای دیتابیس با یکدیگر است (ارتباط بین نودهای etcd برای کلاسترینگ و هماهنگی Raft). کاربران و API Serverها اصلاً با این پورت کاری ندارند.
* `--initial-advertise-peer-urls=https://<MASTER_IP>:2380`
  - آدرسی که این عضو etcd به سایر همتایان (Peers) خود اعلام می‌کند تا دیتابیس‌ها با هم سینک شوند.
* `--listen-metrics-urls=http://127.0.0.1:2381`
  - پورت 2381 برای جمع‌آوری متریک‌های سلامت و کارایی دیتابیس (توسط ابزارهایی مثل Prometheus) استفاده می‌شود.
* تنظیمات امنیتی و رمزنگاری (mTLS):
  - ارتباط با etcd کاملاً رمزنگاری‌شده و دوطرفه است:
    - `--cert-file=/etc/kubernetes/pki/etcd/server.crt`: گواهی عمومی (Public Key) سرور etcd.
    - `--key-file=/etc/kubernetes/pki/etcd/server.key`: کلید خصوصی (Private Key) دیتابیس.
    - `--trusted-ca-file=/etc/kubernetes/pki/etcd/ca.crt`: سرتیفیکیت مرجع صادرکننده (CA) برای تایید هویت کلاینت‌های متصل‌شونده.
---
### 1.3 روش اتصال مستقیم به دیتابیس با etcdctl و مشاهده کلیدها
* ابزار رسمی ارتباط با این دیتابیس etcdctl است. از آن‌جا که دیتابیس در کانتینر ایزوله است و احراز هویت TLS دارد، برای خواندن مستقیم داده‌ها از داخل کلاستر با دستور exec به شکل زیر عمل می‌کنیم:

```bash
kubectl -n kube-system exec -it etcd-public-agent12 -- etcdctl get / \
  --prefix \
  --keys-only \
  --cert="/etc/kubernetes/pki/etcd/server.crt" \
  --cacert="/etc/kubernetes/pki/etcd/ca.crt" \
  --key="/etc/kubernetes/pki/etcd/server.key"
```
* نکات مهم دستور بالا:
    - مسیر / به همراه فلگ --prefix: یعنی هر کلیدی که با این مسیر شروع می‌شود را واکشی کن (مشابه خواندن کل ساختار درخت).
    - فلگ --keys-only: فقط نام کلیدها را نشان بده و محتوای طولانی مقادیر را چاپ نکن.
    - فلگ‌های --cert، --cacert و --key: همان گواهی‌های امنیتی هستند که دسترسی ادمین را به دیتابیس ثابت می‌کنند و مقادیرشان باید دقیقاً با مسیرهای داخل etcd.yaml مطابقت داشته باشد.

## 2. بررسی عمیق kube-apiserver

همان‌طور که گفتیم، API Server **تنها دروازه ورود به کلاستر** و **تنها جزئی است که اجازه دارد با etcd صحبت کند**. هیچ کامپوننتی (نه Scheduler، نه Controller Manager، نه Kubelet و نه کاربر عادی) حق دسترسی مستقیم به دیتابیس etcd را ندارد.

### 2.1 وظایف اصلی kube-apiserver در پردازش یک درخواست:
وقتی دستوری مثل `kubectl apply -f pod.yaml` را می‌زنید، API Server به ترتیب 3 گام زیر را طی می‌کند:

1. **احراز هویت (Authentication):** تو کیستی؟ (بررسی Certificate، توکن یا یوزرنیم/پسورد).
2. **اعتبارسنجی دسترسی (Authorization / RBAC):** آیا اجازه داری این کار را بکنی؟ (بررسی Role و ClusterRole).
3. **کنترل پذیرش (Admission Controllers):** آیا دیتای ارسالی با سیاست‌های امنیتی و سخت‌افزاری کلاستر همخوانی دارد؟ (مثلاً پاد حتماً Resource Limit داشته باشد).

پس از عبور از این سه فیلتر، درخواست روی دیتابیس `etcd` نوشته می‌شود.

---

### 2.2 بررسی فایل kube-apiserver.yaml
مانیفست این کامپوننت در مسیر `/etc/kubernetes/manifests/kube-apiserver.yaml` قرار دارد. مهم‌ترین پارامترهای آن عبارتند از:

* `--secure-port=6443`
  - پورت اصلی و امن ارتباط با API Server. تمام ترافیک ورودی به کلاستر (از سمت kubectl یا ورکرها) روی این پورت شنود می‌شود.
* `--advertise-address=<MASTER_IP>`
  - آی‌پی نود مستر که برای بقیه اجزا اعلام می‌شود تا به آن وصل شوند (معمولاً همان آی‌پی کارت شبکه اصلی مستر).
* `--etcd-servers=https://127.0.0.1:2379`
  - آدرس سرور(های) دیتابیس etcd. اگر etcd کلاستر شده باشد، لیست آی‌پی‌ها با کاما اینجا نوشته می‌شود.
* `--etcd-cafile, --etcd-certfile, --etcd-keyfile`
  - کلیدها و گواهی‌های امنیتی معتبر که API Server برای اثبات هویت خود به etcd تحویل می‌دهد تا دیتابیس اجازه خواندن و نوشتن به آن بدهد.
* `--service-cluster-ip-range=10.96.0.0/12`
  - رنج IP اختصاصی برای سرویس‌های کلاستر (Services). این رنج با رنج پادها (`pod-network-cidr`) کاملاً متفاوت و مجزا است.
* `--client-ca-file=/etc/kubernetes/pki/ca.crt`
  - سرتیفیکیت مرجع (CA) برای چک کردن هویت کلاینت‌ها (مثل kubectl و سایر اجزا).
---
### 2.3 روش‌های صحبت با API Server
دستور `kubectl` در پشت صحنه هیچ جادویی نمی‌کند! صرفاً دستورات شما را تبدیل به متدهای استاندارد **RESTful API** (`GET`, `POST`, `DELETE`, `PUT`) می‌کند و به پورت 6443 می‌فرستد:

* **با kubectl:**
```bash
kubectl get pods
```

## 3. بررسی عمیق kube-controller-manager (موتور کنترلی کلاستر)

اگر API Server منشی کلاستر باشد، Controller Manager **مدیر عملیات یا ناظر کلاستر** است. این بخش مسئول اجرای چرخه‌های کنترلی (Control Loops) در کوبرنتیز است.

### 3.1 چرخه کنترلی (Control Loop) چگونه کار می‌کند؟
یک حلقه نامحدود در پس‌زمینه اجرا می‌شود که مدام این 3 کار را انجام می‌دهد:<br>
[ مشاهده وضعیت فعلی ] ──> [ مقایسه با وضعیت مطلوب ] ──> [ انجام عملیات اصلاحی ]
1. **Watch:** از طریق API Server وضعیت فعلی را بررسی می‌کند.
2. **Compare:** وضعیت فعلی (مثلاً 2 پاد سالم) را با وضعیت مطلوب ثبت‌شده در etcd (مثلاً 3 پاد) مقایسه می‌کند.
3. **Act:** اگر عدم تطابقی وجود داشته باشد، دستور ساخت، حذف یا ویرایش پادها و منابع را صادر می‌کند.
---
### 3.2 انواع کنترلرهای داخل Controller Manager
جالب است بدانید `kube-controller-manager` در واقع **مجموعه‌ای از کنترلرهای مختلف است که در قالب یک باینری/پاد واحد تجمیع شده‌اند** تا مدیریت و اجرای آن‌ها سبک‌تر و راحت‌تر باشد. مهم‌ترین آن‌ها عبارتند از:

* **Node Controller:** 
  - مسئول بررسی سلامت نودهاست. اگر یک نود به مدت مشخصی (پیش‌فرض 40 ثانیه) سیگنال ضربان قلب (Heartbeat) نفرستد، وضعیت آن را `NotReady` می‌کند و اگر این وضعیت طول بکشد، پادهای روی آن را به نود دیگری منتقل می‌نماید.
* **Replication Controller / ReplicaSet Controller:**
  - تضمین می‌کند همیشه به تعداد مشخص‌شده در مانیفست، پاد روی کلاستر بالا و زنده باشد. (اگر پادی کرش کند، این کنترلر پاد جدید درخواست می‌دهد).
* **Endpoints Controller:**
  - اتصال بین پادها و سرویس‌ها (Services) را برقرار و لیست IP پادهای پشت هر سرویس را آپدیت نگه می‌دارد.
* **ServiceAccount & Token Controller:**
  - ساخت اکانت‌های پیش‌فرض و توکن‌های دسترسی API برای Namespaceها.
* **Job Controller:**
  - پیگیری وضعیت پادهایی که برای یک کار مقطعی اجرا شده‌اند تا پس از اتمام با موفقیت خارج (Completed) شوند.

---

### 3.3 بررسی فایل kube-controller-manager.yaml
مانیفست این کامپوننت نیز به صورت Static Pod در مسیر `/etc/kubernetes/manifests/kube-controller-manager.yaml` قرار دارد:
```bash
cat /etc/kubernetes/manifests/kube-controller-manager.yaml
```
### 3.4 مهم‌ترین فلگ‌ها و سوئیچ‌های این فایل:

* `--kubeconfig=/etc/kubernetes/controller-manager.conf`
  - کنترلر منیجر برای صحبت با API Server نیاز به احراز هویت دارد. این فایل شامل سرتیفیکیت‌ها و آدرس API Server است تا کنترلر بتواند مستقیماً با آن ارتباط برقرار کند.
* `--authentication-kubeconfig و --authorization-kubeconfig`
  - تنظیمات امنیتی برای اعتبارسنجی دسترسی‌های خود کنترلر به ریسورس‌های کلاستر.
* `--bind-address=127.0.0.1`
  - مشخص می‌کند این کامپوننت به صورت لوکال روی پورت‌های داخلی به خودش گوش می‌دهد.
* `--leader-elect=true`
  - بسیار حیاتی برای کلاسترهای High Availability (چند مستر): وقتی چند مستر نود داریم، فقط یک Controller Manager باید تصمیم‌گیرنده فعال (Leader) باشد تا دستورات تکراری صادر نشود. بقیه در حالت Standby منتظر می‌مانند تا اگر لیدر قطع شد، رهبری را به دست بگیرند.
* `--node-monitor-period=5s`
  - هر چند ثانیه یک‌بار وضعیت نودها را چک کند.
* `--node-monitor-grace-period=40s`
  - چقدر به نودی که جواب نمی‌دهد مهلت بدهد قبل از اینکه آن را NotReady اعلام کند.
* `--cluster-signing-cert-file و --cluster-signing-key-file`
  - مسیر کلیدها برای صدور اتوماتیک سرتیفیکیت‌های مورد نیاز درون کلاستر.
---
## 4. بررسی عمیق kube-scheduler (تصمیم‌گیرنده مکان استقرار پادها)

کامپوننت `kube-scheduler` وظیفه دارد پادهای تازه متولد شده‌ای را که هنوز به هیچ نودی اختصاص نیافته‌اند (وضعیت `Pending` و فاقد مقدار `nodeName`) شناسایی کرده و بهترین Worker Node را برای میزبانی آن‌ها انتخاب کند.

---
### 4.1 یک تشبیه ملموس (The Dispatcher)
تصور کن در یک شرکت باربری بزرگ کار می‌کنی:
* **مشتری:** بسته‌ای می‌آورد و می‌گوید: «این بسته نیاز به 2 تن جا در ماشین و یخچال با دمای منفی 5 درجه دارد» ➔ **(مفهوم: تعریف پاد با منابع مورد نیاز / Resource Requests)**
* **پارکینگ:** 10 تا کامیون با ظرفیت‌ها و امکانات مختلف پارک شده‌اند ➔ **(مفهوم: نودهای ورکر)**
* **مسئول تخصیص و بارگیری (Dispatcher):** لیست کامیون‌ها را چک می‌کند، آن‌هایی که جا ندارند یا یخچال ندارند را خط می‌زند، و از بین بقیه، بهترین و خلوت‌ترین کامیون را انتخاب کرده و می‌گوید: «این بسته برود روی کامیون شماره 4».

> **نکته بسیار کلیدی:** زمان‌بند (Scheduler) پاد را خودش اجرا نمی‌کند! Scheduler فقط و فقط تصمیم می‌گیرد و انتخاب می‌کند (`Assignment`). بعد از انتخاب، نام نود منتخب را در مشخصات پاد می‌نویسد و کار را به API Server می‌سپارد تا در نهایت `Kubelet` روی همان نود، پاد را استارت بزند.

---
### 4.2 چگونه نود مناسب توسط scheduler انتخاب می‌شود؟ (الگوریتم 2 مرحله‌ای به همراه اتصال نهایی)
فرآیند تصمیم‌گیری scheduler در دو مرحله اصلی انجام می‌شود:
1. فیلتر کردن (Filtering) ──> حذف نودهای نامناسب (کمبود منابع، Taints، پورتهای اشغال):
   - نودهایی که شرط لازم برای اجرای پاد را ندارند از لیست حذف می‌شوند.
   - معیارهای فیلتر:
     - آیا نود رم و CPU کافی دارد؟ (`NodeResourcesFit`)
     - آیا پورتی که پاد می‌خواهد روی این نود آزاد است؟
     - آیا نود Taint خاصی دارد که پاد تحمل آن را ندارد؟
     - آیا شرط‌های NodeSelector یا Affinity پاد روی نود صدق می‌کند؟
2. امتیازدهی (Scoring/Ranking) ──> دادن نمره بین 0 تا 100 بر اساس تعادل بار و سیاست‌ها:
   - از بین نودهایی که از فیلتر عبور کردند، به هر کدام یک نمره (مثلاً از 0 تا 100) داده می‌شود.
   - هدف این مرحله متوازن‌سازی مصرف منابع (Load Balancing) در کلاستر است؛ مثلاً نودی که بار کمتری دارد یا پادهای مرتبط کمتری روی آن است امتیاز بیشتری می‌گیرد.
   - نودی که **بیشترین نمره** را بیاورد به عنوان خانه نهایی پاد انتخاب می‌شود.
3. اتصال (Binding):
   - scheduler نود برنده را به API Server اعلام می‌کند و فیلد `nodeName` در مانیفست پاد به نام نود منتخب تغییر پیدا می‌کند.

### 4.3 بررسی فایل kube-scheduler.yaml
مانیفست این کامپوننت نیز به شکل **Static Pod** در مسیر `/etc/kubernetes/manifests/kube-scheduler.yaml` روی نود مستر قرار دارد:
```bash
cat /etc/kubernetes/manifests/kube-scheduler.yaml
```
### 4.4 مهم‌ترین پارامترها و فلگ‌های این فایل:

* `--kubeconfig=/etc/kubernetes/scheduler.conf`
  - کانفیگ احراز هویت scheduler شامل کلیدها و دسترسی لازم برای مانیتور کردن پادها از طریق API Server.
* `--bind-address=127.0.0.1`
  - گوش دادن به صورت محلی و امن روی لوکال‌هاست نود مستر.
* `--leader-elect=true`
  - همانند Controller Manager، در ساختار Multi-Master و HA تنها یک Scheduler باید در لحظه فعال و تصمیم‌گیرنده باشد تا از تداخل و تخصیص ناهماهنگ جلوگیری شود.
* `--authentication-kubeconfig و --authorization-kubeconfig`
  - تنظیمات دسترسی امن و بررسی توکن‌ها و سرتیفیکیت‌ها.

### 4.5 اگر Scheduler نباشد چه اتفاقی می‌افتد؟
  اگر سرویس یا پاد kube-scheduler متوقف یا حذف شود:
1. تمام پادهای موجود در کلاستر بدون هیچ مشکلی به کار خود ادامه می‌دهند.
2. اما اگر پاد جدیدی بسازید، در وضعیت Pending باقی می‌ماند و بالا نمی‌آید، چون کلاستر نمی‌داند باید آن را به کدام سرور بفرستد!
* نکته: البته می‌توانید به صورت دستی با قرار دادن فیلد nodeName: worker1 در مانیفست پاد، Scheduler را دور بزنید و مستقیماً پاد را روی نود بنشانید.
