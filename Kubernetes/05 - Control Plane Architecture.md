# Control Plane Architecture
در این بخش اجزای اصلی مغز متفکر کلاستر (Control Plane) را بررسی می‌کنیم.
---
### مشاهده پادهای سیستمی
- برای مشاهده پادهای سیستمی از دستور زیر استفاده می‌کنیم
```bash
kubectl get pod -n kube-system
```
در خروجی دستور بالا پادهای سیستمی رو میبینید که مهمترین آن‌ها موارد زیر ‌می‌باشند و در صورتی که هرکدام از موارد زیر بالا نباشه کل کلاستر به مشکل بر میخورد:
`
karimi@Public-Agent12:~$ kubectl get pod -n kube-system
NAME                                     READY   STATUS    RESTARTS     AGE
etcd-public-agent12                      1/1     Running   0            13d
kube-apiserver-public-agent12            1/1     Running   0            13d
kube-controller-manager-public-agent12   1/1     Running   3 (6d ago)   13d
kube-scheduler-public-agent12            1/1     Running   3 (6d ago)   13d
`
---
## 1. etcd
- **تعریف:** یک پایگاه داده Key-Value توزیع شده و فوق‌سریع.
- **وظیفه:** ذخیره وضعیت (State) کل کلاستر. اگر etcd نباشد، کوبرنتیز هیچ چیزی از کلاستر نمی‌داند.
- **نکته کلیدی:** تنها جزء کلاستر است که وضعیت را در دیسک ذخیره می‌کند (Stateful). بقیه اجزا Stateless هستند.
---
## 2. API Server
- **وظیفه:** تنها قطعه‌ای است که با etcd صحبت می‌کند. تمام دستورات kubectl به اینجا می‌آید.
- **نقش:** احراز هویت (Auth) و اعتبارسنجی (Validation) درخواست‌ها.
---
## 3. Controller Manager
- **وظیفه:** بررسی حلقه کنترلی (Control Loop). 
- **مثال:** اگر در etcd نوشته شده ۳ تا پاد باید باشد، اما الان ۲ تا داریم، Controller Manager می‌فهمد که باید یکی دیگر بسازد و به Scheduler دستور می‌دهد.
---
## 4. Scheduler
- **وظیفه:** تصمیم می‌گیرد هر پاد روی کدام Worker Node قرار بگیرد (با توجه به منابع مثل CPU و RAM).
---
### فایل‌های سیستمی به صورت پیشفرش در دایرکتوری زیر ذخیره می‌شوند:
/etc/kubernetes/manifests/<br>
├── etcd.yaml<br>
├── kube-apiserver.yaml<br>
├── kube-controller-manager.yaml<br>
└── kube-scheduler.yaml<br>
#### نکته: برای exec کردن پاد مورد نظر از دستور زیر استفاده می‌کنیم:
```bash
kubectl exec -it -n <nsname> <podname> -- bash/sh
kubectl exec -it -n kube-system etcd-public-agent12 sh
```
### 1.1 بررسی etcd.yaml
مانیفست این کامپوننت در مسیر `/etc/kubernetes/manifests/etcd.yaml` قرار دارد. مهم‌ترین پارامترهای آن عبارتند از:
* `--secure-port=6443`
  - پورت اصلی و امن ارتباط با API Server. تمام ترافیک ورودی به کلاستر (از سمت kubectl یا ورکرها) روی این پورت شنود می‌شود.
* `--cert-file=/etc/kubernetes/pki/etcd/server.crt`<br>
  - این آدرسی هست cert مربوط به اتصال به دیتابیس در آن ذخیره شده است، درواقع این تنظیمات همان publickey اتصال به دیتابیس می‌باشد.
* `--key-file=/etc/kubernetes/pki/etcd/server.key`<br>
  - این تنظیمات هم درواقع همان privatekey تنظیمات اتصال به دیتابیس می‌باشد.
* `--trusted-ca-file=/etc/kubernetes/pki/etcd/ca.crt`<br>
  - این تنظیمات هم درواقع همان آدرسی است که certificate از آن صادر شده است.
* `--listen-client-urls=https://127.0.0.1:2379,https://192.168.57.49:2379`<br>
  - این گزینه پورت دیتابیس را به ما نمایش می‌دهد، یعنی دیتابیس روی پورت 2379 بالا می‌باشد و به صورت لوکالی می‌توان به دیتابیس متصل شد.
* `--advertise-client-urls=https://192.168.57.49:2379`<br>
  - این گزینه پورت دیتابیس را به ما نمایش می‌دهد، یعنی دیتابیس روی پورت 2379 می‌باشد و برای کاربرانی می‌باشد که می‌خواهند از خارج از سرور فعلی به دیتابیس متصل شوند، به عنوان مثال شما 3 سرور دارید که دیتابیس را روی سرور مستر آپ کردید در همان سرور مستر می‌توانید با آی‌پی لوکالی به دیتابیس متصل شوید ولی اگر از سرورهای ورکر بخواهید به دیتابیس متصل شوید باید از advertise-client-urls استفاده نمایید.
* `--listen-peer-urls=https://192.168.57.49:2380`<br>
  - این گزینه برای زمانی استفاده می‌شود که هرکسی بغیر از یوزرهای عادی بخواهد به دیتابیس متصل شود درواقع این تنظیمات و پورت برای ارتباط داخلی دیتابیس‌ها باهم می‌باشد مثلا شما بخواهید چند دیتایس etcd را با هم کلاستر کنید.
* `--listen-metrics-urls=http://127.0.0.1:2381`<br>
  - این تنظیمات مربوط به مانیتورنگ دیتابیس می‌باشد.
* `--data-dir=/var/lib/etcd`<br>
  - مسیری هست که اطلاعات دیتابیس در آن ذخیره می‌شود.
### 1.2 روش اتصال به دیتابیس و مشاهده کلیدها
* برای اتصال به دیتابیس و مشاهده کلیدها و مقدارها از دستور زیر استفاده میکنیم:
```bash
kubectl -n kube-system exec -it etcd-public-agent12 -- etcdctl get / --cert="/etc/kubernetes/pki/etcd/server.crt" --cacert="/etc/kubernetes/pki/etcd/ca.crt" --key="/etc/kubernetes/pki/etcd/server.key" --prefix --keys-only
```
* نکات:
    - اگر دقت کنید در دستور بالا مسیر / مشخص شده است این یعنی تمام کلیدها و مقدارهایی که در این مسیر هستند را نمایش بده.
    - برای اتصال به دیتابیس دقیقا همانند بقیه دیتابیس‌ها نیازمند دسترسی یا همان یوزر و پس هستیم که همانطور که در دستور مشخص است  با مقادیر زیر مشخص شده است:<br>
    --cert<br>
    --cacert<br>
    --key<br>
    مقادیر آن‌ها باید دقیقاً با مقداری که در فایل etcd.yaml هست یکی باشد.

## 2. بررسی عمیق kube-apiserver

همان‌طور که گفتیم، API Server **تنها دروازه ورود به کلاستر** و **تنها جزئی است که اجازه دارد با etcd صحبت کند**. هیچ کامپوننتی (نه Scheduler، نه Controller Manager، نه Kubelet و نه کاربر عادی) حق دسترسی مستقیم به دیتابیس etcd را ندارد.

### 2.1 وظایف اصلی kube-apiserver در پردازش یک درخواست:
وقتی دستوری مثل `kubectl apply -f pod.yaml` را می‌زنید، API Server به ترتیب ۳ گام زیر را طی می‌کند:

1. **احراز هویت (Authentication):** تو کیستی؟ (بررسی Certificate، توکن یا یوزرنیم/پسورد).
2. **اعتبارسنجی دسترسی (Authorization / RBAC):** آیا اجازه داری این کار را بکنی؟ (بررسی Role و ClusterRole).
3. **کنترل پذیرش (Admission Controllers):** آیا دیتای ارسالی با سیاست‌های امنیتی و سخت‌افزاری کلاستر همخوانی دارد؟ (مثلاً پاد حتماً Resource Limit داشته باشد).

پس از عبور از این سه فیلتر، درخواست روی دیتابیس `etcd` نوشته می‌شود.

---

### 2.2 بررسی فایل kube-apiserver.yaml
مانیفست این کامپوننت در مسیر `/etc/kubernetes/manifests/kube-apiserver.yaml` قرار دارد. مهم‌ترین پارامترهای آن عبارتند از:

* `--secure-port=6443`
  - پورت اصلی و امن ارتباط با API Server. تمام ترافیک ورودی به کلاستر (از سمت kubectl یا ورکرها) روی این پورت شنود می‌شود.
* `--advertise-address=<MASTER_IP>`
  - آی‌پی نود مستر که برای بقیه اجزا اعلام می‌شود تا به آن وصل شوند (معمولاً همان آی‌پی کارت شبکه اصلی مستر).
* `--etcd-servers=https://127.0.0.1:2379`
  - آدرس سرور(های) دیتابیس etcd. اگر etcd کلاستر شده باشد، لیست آی‌پی‌ها با کاما اینجا نوشته می‌شود.
* `--etcd-cafile, --etcd-certfile, --etcd-keyfile`
  - کلیدها و گواهی‌های امنیتی معتبر که API Server برای اثبات هویت خود به etcd تحویل می‌دهد تا دیتابیس اجازه خواندن و نوشتن به آن بدهد.
* `--service-cluster-ip-range=10.96.0.0/12`
  - رنج IP اختصاصی برای سرویس‌های کلاستر (Services). این رنج با رنج پادها (`pod-network-cidr`) کاملاً متفاوت و مجزا است.
* `--client-ca-file=/etc/kubernetes/pki/ca.crt`
  - سرتیفیکیت مرجع (CA) برای چک کردن هویت کلاینت‌ها (مثل kubectl و سایر اجزا).
