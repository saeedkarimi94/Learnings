معماری کوبرنتیز به دو بخش اصلی تقسیم می‌شود: Master Node (Control Plane) و Worker Nodes.

* **Master Node (کشتی فرماندهی)**: مرکز مدیریت، برنامه‌ریزی و تصمیم‌گیری است.
* **Worker Node  (کشتی‌های حمل بار)**: سرورهایی هستند که وظیفه دارند کانتینرهای اپلیکیشن شما را عملاً روی خود حمل و اجرا کنند.

## **Master Node (Control Plane)**:
مستر نود به عنوان مغز متفکر کلاستر عمل می‌کند و وظیفه‌ی نظارت بر سلامت کل سیستم، تصمیم‌گیری برای اجرای پادها و پاسخ به درخواست‌های کاربر را دارد. اجزای کلیدی آن عبارتند از:

* **kube-apiserver (درگاه ارتباطی)**: تنها نقطه‌ای که با کاربر و سایر اجزا حرف می‌زند و تمام درخواست‌ها را احراز هویت و اعتبارسنجی می‌کند.
* **ETCD (دیتابیس کلاستر)**: وضعیت کل کلاستر را ذخیره می‌کند.
* **kube-scheduler (مسئول تخصیص بار)**: تصمیم می‌گیرد که هر کانتینر/پاد بر اساس منابع موجود روی کدام کشتی (Worker Node) بارگیری شود.
* **kube-controller-manager (ناظر و تنظیم‌کننده)**: حلقه‌های کنترلی که مدام وضعیت فعلی کلاستر را با وضعیت مطلوب (Desired State) مقایسه می‌کنند (مثلاً اگر پادی بمیرد، یکی جدید جایگزین می‌کند).

## **ETCD Cluster**:
در معماری کوبرنتیز، ETCD حکم مغز و حافظه‌ی کلاستر (Single Source of Truth) را دارد.

به زبان ساده: هر چیزی که در کوبرنتیز تعریف می‌کنید (پادها، سرویس‌ها، Secretها، ConfigMapها، وضعیت سلامت نودها، Deploymentها و…) در قالب داده‌های کلید-مقدار (Key-Value) داخل etcd ذخیره می‌شود. اگر etcd نباشد یا از کار بیفتد، کوبرنتیز عملاً هیچ اطلاعی از وضعیت کلاستر نخواهد داشت.
### مشخصات و ویژگی‌های کلیدی ETCD:
* **دیتابیس Key-Value توزیع‌شده (Distributed Key-Value Store)**:
داده‌ها به صورت درختی و کلید-مقدار ذخیره می‌شوند (مثلاً مسیر /registry/pods/default/my-pod).
به زبان Go نوشته شده و بر پایه استاندارد ارتباطی gRPC و پروتکل Raft کار می‌کند.
* **یکپارچگی قوی داده‌ها (Strong Consistency)**:
طبق قضیه CAP، دیتابیس etcd در دستهٔ CP (Consistency & Partition Tolerance) قرار دارد؛ یعنی در صورت قطعی شبکه یا خطای نود، «صحت و هماهنگی داده‌ها» را به «در دسترس بودن ناقص» ترجیح می‌دهد تا هیچ‌وقت دادهٔ مغایر (Inconsistent) ثبت نشود.
* **سیستم نظارت و رویدادها (Watch Mechanism)**:
یکی از قدرتمندترین ویژگی‌های etcd امکان Watch است. اجزایی مثل Controller Manager و Scheduler به جای Queryهای متوالی (Polling)، به etcd گوش می‌دهند تا به محض تغییر یک کلید (مثلاً ساخته شدن پاد جدید)، سریعاً مطلع شوند و واکنش نشان دهند.
### نکات طلایی نگهداری ETCD:
* **تنها kube-apiserver حق ارتباط با ETCD را دارد**: هیچ پاد، ورکر یا کنترولری نباید و نمی‌تواند مستقیماً به etcd وصل شود؛ همه چیز از درگاه kube-apiserver رد می‌شود.
* **حساسیت شدید به دیسک (Disk I/O)**: نوشتن logهای Raft (WAL) به شدت به تأخیر دیسک حساس است. روی سرورهای etcd حتماً باید از Fast SSD / NVMe با IOPS مناسب استفاده شود.
* **بکاپ‌گیری منظم با etcdctl**: گرفتن Snapshot منظم قبل از هرگونه تغییر یا به‌روزرسانی حیاتی است:

## **Controller Manager**:
در معماری کوبرنتیز، kube-controller-manager را می‌توان «نگهبان و ضامن وضعیت کلاستر» دانست.

به زبان ساده: اگر مستر نود را مرکز فرماندهی کلاستر بدانیم، کنترلر منیجر وظیفه دارد مدام کلاستر را زیر نظر بگیرد تا وضعیت واقعی (Current/Actual State) همیشه با وضعیت دلخواه شما (Desired State) یکسان بماند.
**چرا به آن Controller Manager می‌گویند؟** در دل کوبرنتیز ده‌ها کنترلر مختلف برای وظایف گوناگون وجود دارد. برای اینکه نیازی نباشد ده‌ها پروسس جداگانه روی مستر اجرا شود و پیچیدگی بالا برود، تمام این کنترلرها در یک فایل باینری و یک پروسس واحد به نام kube-controller-manager جمع شده‌اند.

## **kube-apiserver**:
در معماری کوبرنتیز، kube-apiserver دقیقاً «قلب تپنده و دروازهٔ اصلی کلاستر» است، هیچ ارتباطی در کوبرنتیز بدون هماهنگی و عبور از API Server اتفاق نمی‌افتد. چه دستور kubectl get pods را از ترمینال خودتان بزنید، چه یک پاد بخواهد با کلاستر صحبت کند، و چه اجزایی مثل Scheduler، Kubelet و Controller Manager بخواهند کاری انجام دهند، همگی فقط و فقط با kube-apiserver گفتگو می‌کنند.

* **چرخه زندگی یک درخواست در API Server**:
وقتی شما دستوری مانند kubectl apply -f deployment.yaml ارسال می‌کنید، API Server درخواست را طی ۴ مرحلهٔ متوالی اعتبارسنجی و پردازش می‌کند:

                  ┌───────────────────────────────┐
                  │    Request (e.g. kubectl)     │
                  └───────────────┬───────────────┘
                                  │
                                  ▼
                  1. Authentication (کیستی؟)
               [بررسی هویت، گواهی TLS، توکن یا OIDC]
                                  │
                                  ▼
                  2. Authorization (اجازه داری؟)
                 [بررسی دسترسی RBAC / Role / ClusterRole]
                                  │
                                  ▼
               3. Admission Control (قوانین و اعتبارسنجی)
            [اعمال سیاست‌ها: Mutating & Validating Webhooks]
                                  │
                                  ▼
                  4. Save to ETCD (ثبت در دیتابیس)
               [تنها نقطه‌ای که با etcd گفتگو می‌کند]

* **نکته**: هیچ کامپوننتی مستقیماً با دیتابیس یا همان ETCD در ارتباط نیست، وظیفه برقراری ارتباط با ETCD بر عهده kube-apiserver می‌باشد.

## **Worker Node**:
ورکر نودها سرورهایی هستند که بار کاری واقعی (Workload / Containers) روی آن‌ها اجرا می‌شود. هر ورکر نود شامل سه بخش اساسی است:
* **kubelet (کاپیتان کشتی)**: یک Agent است که روی تک‌تک ورکرها اجرا می‌شود.
دستورات را از kube-apiserver دریافت می‌کند و مطمئن می‌شود کانتینرهای مشخص‌شده در پاد سالم هستند و اجرا می‌شوند.
* **kube-proxy (افسر مسیریابی و شبکه)**: مدیریت شبکه و قوانین فایروال (iptables / IPVS) را روی نود بر عهده دارد تا سرویس‌ها (Service) و پادها بتوانند در داخل و خارج کلاستر با هم ارتباط برقرار کنند.
* **Container Runtime (موتور اجرای کانتینر)**: نرم‌افزاری که کانتینرها را از رجیستری دانلود (Pull) کرده و Run می‌کند (مثل containerd، CRI-O یا در گذشته Docker).
